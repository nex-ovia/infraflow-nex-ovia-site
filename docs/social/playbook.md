## The trust habits

1. **Ship before you post.** Every post points at something real: a release, a repo, a page, a result.
2. **Date everything.** Release tags, post dates and the /impact page should all agree.
3. **Link back home.** Long posts end with one link to nex-ovia.com (a page, not the homepage).
4. **Show the failures too.** A post about what broke and how I fixed it builds more trust than a win.
5. **Credit people.** Tag collaborators and the projects I build on.
6. **Keep a monthly snapshot.** First of each month: screenshot follower and post analytics on every platform, note
   GitHub stars, downloads and releases, and save an archive.org snapshot of nex-ovia.com and /impact.
7. **Say yes to visible roles:** meetup and conference talks, podcast interviews, hackathon judging, reviewing talks
   or papers, guest articles in trade publications. Each one is a dated record someone else published.

## Ready-to-post drafts

### 1. Implementation strategy (LinkedIn)
Most failed implementations don't fail in the code. They fail in the order things were done.

Before anyone writes a line, I answer four questions:
→ What has to be true for the customer on day one?
→ What's the riskiest assumption, and how do we test it first?
→ What does "done" look like in a way both the business and the engineers agree on?
→ Who owns this a year from now?

AI makes the building faster. It doesn't answer any of these for you.

### 2. Build log (LinkedIn)
Last night I rebuilt my website while I slept. Sort of.

I set the plan and wrote the copy. Small AI agents made the edits, each one in its own sandbox. Every change had to
pass the same checks before I'd merge it: tests, a full build, a broken-link scan, and screenshots on a phone and a
laptop.

Two things the checks caught that a confident AI wouldn't have told me:
→ one agent "passed" by quietly rewording a note instead of fixing the code
→ the phone version had been hiding the menu completely

Nothing went live until I approved it. AI does the typing. I own the outcome.

### 3. After the demo (LinkedIn)
My first job was keeping Linux mail servers alive for clients.

The lesson I still use every week: the demo is the easy part. The real work starts when it has to run at 2am, when
the person who built it has left, and when someone asks "why does it do that?"

That's why I wrote NXS: four rules so whatever gets built, by a person or by AI, can still be explained, changed and
moved by whoever comes next. It's free and open: github.com/nex-ovia/NXS

### 4. NXS in practice (X thread)
AI made code cheap. It didn't make understanding cheap.

4 rules I use so I still own what AI builds:
1/ Logic lives apart from tools. Change vendors, keep the logic.
2/ Nothing environment-specific inside the code.
3/ Every dependency named and written down.
4/ Anyone can run it from what's written. No hero required.
Open standard, free to use: github.com/nex-ovia/NXS

### 5. Open source (X / short video script)
coderev v0.30 is out. 57 releases since June.
One command: it scans your code, maps it, and only then asks AI to review what matters.
Rules first, AI second. Free and open source.
brew install srivastava-ami/tools/coderev

### 6. Leading technical teams (LinkedIn)
At one point I owned every iOS and Android SDK integration question our enterprise customers had.

So I stopped answering the same question twice. I wrote sample apps and small Python tools, and integrations got
faster for everyone.

That's still how I lead teams: find the question your team answers every week, and build the thing that answers it.

## Rules for every post
- One real thing per post: a screenshot, a number, a moment, a link.
- End with a question or a link, never both.
- Never name employers' customers or share internal details.
- Reuse: every long post becomes one X post and one carousel.
