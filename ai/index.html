AI-driven leadership

AI writes the code. I own the outcome.

I use AI agents every day, the way I'd lead a team: I decide what gets built, they do the typing, and nothing ships until it passes checks and I've reviewed it. Here's exactly how that works.

The operating model

01

Plan

I write the intent, constraints and acceptance checks as a plan in plain TOML, before any code exists. The plan is the contract.

02

Chunk

The plan is cut into the smallest independent units: one function, one page, one config change. Each chunk carries its own validation gate.

03

Dispatch

A dispatcher sends each chunk to an AI worker in an isolated git worktree. Cheap, fast models take routine chunks; stronger models take hard ones.

04

Validate

Nothing is accepted on the model's word. Tests, builds, linters and policy checks run automatically; a failed gate isolates the failure to one small chunk.

05

Approve

I review the diff, merge it, and every change to production waits behind a human approval gate. The AI proposes; a person decides.

Guardrails that make it work

Shared context, not chat history

Every agent reads the same project manifest: decisions, rules and current state live in the repo, not in someone's head or a chat window.

Least privilege by default

Workers get only the tools a chunk needs. Cloud access uses short-lived OIDC identities instead of stored secrets.

Agent-agnostic

The same configuration drives Claude Code, OpenCode, Pi and others, so the workflow outlives any single vendor. That's NXS rule one applied to AI.

Evidence over confidence

Every recommendation cites a file, a command output or a source. Claims without evidence don't ship.

Built this way

This website, its infrastructure and the tools below were built with this model: plans and chunk specs are committed alongside the code, so you can see exactly how.
