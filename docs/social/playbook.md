## Ready-to-post drafts

### 1. Build log (LinkedIn)
Last night I rebuilt my website while I slept. Sort of.

I wrote the plan and the copy. Small AI agents did the edits, each one in its own sandbox. Every change had to pass
the same checks before I'd merge it: tests, a full build, a broken-link scan, and screenshots on a phone and a laptop.

Two things the checks caught that a confident AI wouldn't have told me:
→ one agent "passed" by quietly rewording a note instead of fixing the code
→ the phone version had been hiding the menu completely

Nothing went live until I approved it. That's the whole idea: AI does the typing, I own the outcome.

How are you keeping control of what AI builds for you?

### 2. After the demo (LinkedIn)
My first job was keeping Linux mail servers alive for clients.

The lesson I still use every week: the demo is the easy part. The real work starts when it has to run at 2am, when
the person who built it has left, and when the customer asks "why does it do that?"

That's why I wrote NXS. Four rules so that whatever gets built, by a person or by AI, can still be explained,
changed and moved by whoever comes next.

### 3. Owning AI-built work (X thread)
AI made code cheap. It didn't make understanding cheap.

4 rules I use so I still own what AI builds:
1/ Logic lives apart from tools. Change vendors, keep the logic.
2/ Nothing environment-specific inside the code.
3/ Every dependency named and written down.
4/ Anyone can run it from what's written. No hero required.
That's NXS. It's open: github.com/nex-ovia/NXS

### 4. Leading without coding (LinkedIn)
"I'm not technical enough to lead this project."

I hear this from managers all the time. You don't need to read code to lead a technical project. You need to see
what was built, what it depends on, and how to change it safely, in plain language.

That's what I built genome for: one file describes the project, and it becomes a map anyone can read and approve.

### 5. Tools (X / short video script)
coderev in one command: it scans your code, maps it, and only then asks AI to review what matters.
Rules first, AI second. Cheaper, faster, and the AI can't wander off.
brew install srivastava-ami/tools/coderev

### 6. After the demo (LinkedIn)
At one point I owned the iOS and Android SDK integration questions for every enterprise customer we had.

So I stopped answering the same question twice. I wrote sample apps and small Python tools, and integrations got
faster for everyone.

Most "AI transformation" is that same move. Find the question you answer every week, and build the thing that
answers it for you.

## Rules for every post
- One real thing per post: a screenshot, a number, a moment. No generic advice.
- End with a question or a link, never both.
- Don't name employers' customers.
- Reuse: every long post becomes one X post and one carousel.
